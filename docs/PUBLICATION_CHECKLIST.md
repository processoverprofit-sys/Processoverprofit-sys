# Public documentation publication checklist

This checklist applies to public documentation only. Completing it does not authorise private application execution, changes to repository settings, release of private evidence or live trading.

## Before opening a pull request

- [ ] Review the exact files and scope; include only approved public material.
- [ ] Remove private code, credentials, wallet information, signing material, internal paths, logs, personal identifiers and unpublished evidence. Do not paste them into the PR itself.
- [ ] Check images and attachments for visible identifiers and metadata. Publish only separately approved assets.
- [ ] Label design objectives, historical records, fictional examples and observed results accurately.
- [ ] Confirm rights to publish third-party material; retain existing rights notices.
- [ ] Check Markdown links and headings, readability and consistency with both project descriptions.
- [ ] Follow [SECURITY.md](../SECURITY.md) for confidential concerns. Do not publish vulnerability details.
- [ ] Check the public author and committer identity, the changed-file list and the intended base branch.

## Before and after publication

- [ ] Obtain explicit maintainer approval of the exact review candidate before merging.
- [ ] Do not bypass branch rules, change access or settings, or attach private evidence.
- [ ] After an authorised merge, verify the published content and preservation of existing protections.
- [ ] If a sensitive disclosure is suspected, stop publication; do not reproduce the material in a public report.

A checkbox is a review aid, not proof of security. Use the [evidence report template](EVIDENCE_REPORT_TEMPLATE.md) only for separately reviewed, approved evidence. See [Stage 7](STAGE7_SECURITY_QUALITY_REVIEW.md) for unresolved configuration verification.
